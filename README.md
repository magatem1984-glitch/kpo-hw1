# ВышКат — ДЗ №1 по КПО

Простое консольное приложение на C# и .NET 8. Транспорт проходит техосмотр перед приёмкой. Программа учитывает вещи, считает количество и энергию, выводит инвентарные номера и транспорт для новичков.

## Где что находится

| Файл | Содержание |
| --- | --- |
| `VyshKat/Models.cs` | Интерфейсы, транспорт и вещи |
| `VyshKat/Services.cs` | Техосмотр и учёт парка |
| `VyshKat/Program.cs` | DI-контейнер и консольное меню |
| `VyshKat.Tests/Tests.cs` | Все тесты |

Остальные файлы нужны для сборки, запуска и демонстрации. Всего в архиве 10 файлов.

## Запуск

Установить [.NET 8 SDK](https://dotnet.microsoft.com/download/dotnet/8.0). Открыть терминал в папке с `VyshKat.sln`:

```bash
dotnet build
dotnet test
dotnet run --project VyshKat
```

В меню можно добавить транспорт или вещь, посмотреть отчёт, список для новичков и весь инвентарь. Данные вводит пользователь. Тормоза и колёса: 1 — исправны, 0 — неисправны. Расход энергии можно вводить с точкой или запятой. Данные хранятся в памяти до выхода.

## Демонстрация

Файл `examples/demo.txt` содержит готовый ввод. В программе демонстрационные объекты не прописаны.

В WSL, Linux, macOS или Windows CMD:

```bash
dotnet run --project VyshKat < examples/demo.txt
```

В PowerShell:

```powershell
Get-Content -Encoding UTF8 examples/demo.txt | dotnet run --project VyshKat
```

Сценарий показывает пустой парк, приём трёх видов транспорта, отказ неисправному самокату, добавление вещей, все отчёты и повторный инвентарный номер. Итог: 3 транспортных средства, 2 вещи, 8 кВт·ч в сутки. Новичкам подходят S1 и E1; велосипед B1 с простотой 5 не подходит.

## Решения и SOLID

В `Models.cs` интерфейс `IInventoryObject` задаёт название и номер, а `IEnergyConsumer` — суточный расход. `InventoryObject` хранит общие данные. От него наследуются `Transport` и `Thing`. Электрический транспорт дополнительно реализует потребление энергии; шлем и обычный велосипед этого интерфейса не имеют.

В `Services.cs` сервис `ServiceCenter` проверяет тормоза и колёса. Их состояние вводит оператор, решение о приёмке принимает сервис. `FleetService` хранит принятый транспорт и вещи. Номера уникальны без учёта регистра. Отклонённый транспорт не участвует в отчётах и не занимает номер. Энергия суммируется у всех потребителей на балансе, включая зарядные станции; введённые расходы предполагаются отдельными, без двойного учёта. Вещи добавляются без техосмотра транспорта.

- **SRP:** меню отвечает за ввод и вывод, `ServiceCenter` за техосмотр, `FleetService` за учёт.
- **OCP:** отчёты работают с общими типами и интерфейсами. Новый транспорт не требует изменения `FleetService`.
- **LSP:** все наследники `Transport` обрабатываются одинаково и сохраняют общие ограничения.
- **ISP:** инвентарный учёт и расход энергии разделены. Шлему не нужен расход энергии.
- **DIP:** `FleetService` получает `IServiceCenter` через конструктор. Реализацию выбирает DI-контейнер в `Program.cs`.

## Обязательные вопросы

**Самый явный принцип:** DIP. `FleetService` не создаёт техосмотр самостоятельно, а получает интерфейс. В тестах его можно заменить.

**Что сознательно ограничено:** OCP в консольном меню. Чтобы добавить новый вид, нужно изменить выбор типа в `ConsoleApp.AddTransport` или `AddThing`. Для небольшой программы это проще отдельного реестра фабрик. Для `FleetService` отдельный интерфейс не нужен: второй реализации пока нет.

**Что будет при расширении:** новый транспорт требует класса и пункта меню; отчёты останутся прежними. Сотрудников нельзя наследовать от `InventoryObject`, поскольку их не ставят на баланс; им нужен отдельный учёт. Запчасти можно наследовать от `Thing`, а для отдельного склада добавить сервис хранения.

**Какие тесты проверяют правила:** в `Tests.cs` тест `ServiceCenter_ChecksBrakesAndWheels` проверяет техосмотр, `BeginnerTransport_UsesThresholdSix` — границу 5/6. `AddTransport_UsesInspectionResultFromDi` регистрирует `FakeServiceCenter` вместо `IServiceCenter` в настоящем DI-контейнере и проверяет приём и отказ. Есть проверки отчётов, номеров и консольного ввода.

**Роль ИИ:** ИИ помог с реализацией кода для тестов и Readme.md. Самостоятельно выполнены реализация остального кода, сборка проекта, запуск тестов и проверка работы приложения.

Покрытие можно измерить командой `dotnet test --collect:"XPlat Code Coverage"`. Отчёт будет в подпапке `VyshKat.Tests/TestResults`.

## Сдача

Если учебный репозиторий не выдан, предполагаемый порядок: создать свой репозиторий GitHub с начальным README в `main`, создать ветку `hw1`, загрузить в неё исходники из архива и открыть PR: **base: main**, **compare: hw1**. Ссылку на PR отправить в форму преподавателя. Если преподаватель даст другой порядок, следовать ему. Папки `bin`, `obj`, `TestResults` в репозиторий не загружать.

Оценку определяет проверяющий. По условию при отказе от защиты оценки 9 и 10 снижаются до 8; намеренно убирать обязательные требования не нужно.
